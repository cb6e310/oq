## 本次已落地

1. `engine.py`：NumPy 粗筛为每只股票预计算状态直方图与二元事件累计计数，在多个长度和重叠窗口之间复用；原来每个桶反复收集窗口状态、分别统计三种取值、求事件最大值的操作改为累计计数差分。状态计数并列时仍选最低状态值，事件仍使用已有二元通道。扫描步长、候选预算、最终评分没有调整。
2. elastic 诊断增加 `coarse_backend`、`dtw_backend`、`recall_s`、`candidate_selection_s`、`rerank_s`、`total_s`。计时随现有诊断写入结果和查询历史；它们是完成后的统计，还没有接成网页实时进度。
3. `benchmark.py` 增加 `--elastic-coarse-step`，便于明确比较步长 1 和 8。
4. 增加跨 2048 窗口批次边界、不同长度、状态计数并列、空事件、关闭成交量通道的数值对照测试。

测试：实际无 Numba 环境共 28 项，26 项通过，2 项编译核对照因缺依赖跳过；临时 Numba 环境 28 项全部通过。样本优化前后 Top20 全字段完全一致。现有未提交修改已保留；编写报告时的旧状态是服务尚未加载 NumPy 优化，之后按用户请求已启用 Numba 并重启服务。

## 后续优化优先级

| 优先级 | 优化 | 收益与约束 |
| --- | --- | --- |
| P0 | 在实际服务环境启用 Numba，明确提供步长 1 / 稀疏扫描设置，并显示当前后端 | 编译优化和召回范围选择应分别可控；同精度抽样已验证约 4.3 倍加速，完整步长 1 尚未跑基准 |
| P1 | 历史搜索在粗筛前按 `date < query_start` 裁剪行情前缀 | 目前所有长度距离算完才屏蔽未来窗口；早期历史查询浪费更明显。本次查询接近数据末端，预期收益有限；必须保持候选位置、首根前收盘价等语义 |
| P1 | 流式维护有限候选堆，保留特殊事件、structure 路径和全局各自名额 | 原任务保留约 130 万个 Python 字典后才筛成 1000，增加内存与对象分配；编译完整扫描仍有约 113 万候选。必须核验重复项、并列排序和保留名额，不能直接减少 recall_n |
| P1 | 真正的协作取消、单任务队列、任务各自持有统计 | 当前 cancel 只改变 job 状态；计算内核未接收取消信号，直到图表生成后才检查。取消后重搜会导致后台任务重叠；共享 engine.last_search_stats 也可能串任务 |
| P2 | 稀疏粗筛后，对有限短名单做起点邻域补搜 | 步长 8 对短形态起点有明显影响；对短名单补搜 ±7 根后再精排，评估召回质量，而不是直接把稀疏扫描宣称为完全等价 |
| P2 | 缓存股票/周期的事件和状态特征，按数据版本失效 | 相同数据库和周期重复搜索可以复用；避免不受限地缓存每个查询产生的大距离矩阵 |
| P2 | 分阶段实时进度和错误/运行日志 | 页面定时器会持续覆盖为“扫描历史行情”，无法反映已到精排或绘图；当前新增的是完成后计时，仍需接实时回调 |
| P3 | 处理取消、共享状态后，再评估多核批处理 | 当前 Python 动态规划及对象组织不适合简单增加搜索线程；批处理需控制内存、任务隔离和编译核运行方式 |

不建议优先减少精排预算或切换 fixed：两者都可能改变搜索质量或匹配定义，而这次已经定位到明确的执行后端与重复统计开销。
